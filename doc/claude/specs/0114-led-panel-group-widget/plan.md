# Plan 0114 — LED Panel as a Group Widget

> **Phase 2 of 4 — the HOW.** The technical design that satisfies every requirement in
> [`spec.md`](./spec.md). Read the relevant `doc/claude/` sub-docs and the *actual code*
> before writing this — a plan grounded in a stale mental model is worse than no plan.
> Gate: do not start `/ss-tasks` until a human marks this `approved`.

## Approach (one paragraph)

Add `GroupWidget::LEDPanel` (slug `ledpanel`, appended after `BarPanel`) and map it to the
existing dashboard type `DashboardLED = 8`, so the `UI::Widgets::LEDPanel` model, its QML, the
persisted `widgetType` in layouts and external windows, and every workspace reference keep
working unchanged. Delete the per-dataset `Led` property from the registry and regenerate; drop
the phantom-group assembly in `WidgetMapBuilder`, the LED special cases in the workspace
plumbing, and the `DatasetLED` option bit. One Core-level helper derives an LED Panel group from
a source group and a list of member positions; the loader's one-shot migration and the nine
project generators and importers that today set `led = true` on boolean tags all call it, so
the migrated file and a freshly generated one have the same shape. The migration keys on the
presence of the old flag in the raw JSON, not on a schema bump, because the loader's existing
older-schema block clears every workspace.

## Architecture & data flow

Nothing moves between threads or stages. A project's `Group::widget == "ledpanel"` resolves to
`DashboardLED` in `getDashboardWidget`, `WidgetMapBuilder::buildWidgetGroups` buckets the whole
group under that key exactly as it does for Bar Panel, `DashboardWidget` instantiates
`UI::Widgets::LEDPanel(relativeIndex)` as today, and the model reads the bucketed group
positionally each tick. The alarm side is untouched because `AlarmMonitor::rebuildTrackers`
already walks `(group, dataset)` pairs through `datasetRaisesBandAlarms`, which inherits the new
group branch of `datasetRendersAlarmBands`. Workspace references and external windows persist
`widgetType = 8` with a relative index; because the migration inserts each LED Panel directly
after its source group, the relative order of LED Panels is the one the phantom builder produced,
so saved references resolve to the same panel. The derived-group helper lives in Core so the
loader (Pipeline), the importers (Pipeline) and the driver project generators (Devices) share
one definition of "an LED Panel split off a group".

## Hotpath & threading impact

- **Touches the hotpath?** No. `WidgetMapBuilder` runs at rebuild rate; `LEDPanel` reads at UI
  tick; `FrameBuilder`, `FrameReader`, `CircularBuffer` and the span lane are untouched. The
  copies share the source dataset's `index`, which is already legal (bit fields on one word),
  and `FrameBuilder` indexes columns by `index`, so no new per-frame work.
- **New cross-thread signal/slot?** No.
- **New input to a cached hotpath flag?** No.
- **Timestamp ownership** — unaffected.
- **Allocation on the publish path** — none added; the derived group is built at load, import
  or generation time only.

## Data model & persistence

- `Dataset::led` and the `led` JSON key leave the struct and the writer. `Keys::LED` stays as
  the legacy key for the loader's raw peek.
- `kSchemaVersion` stays 3. The migration gate is "any raw dataset has `led == true`"; the
  writer never emits the key, so a migrated save cannot trigger it again (R7). Bumping the
  schema would also fire the loader's older-schema block, which clears every workspace list.
- Insertion order: after `seedNextUniqueIdFromGroups` (so allocation is safe), after the
  `legacyUniqueIds` migrations (which treat group ids positionally) and after
  `migrateLegacyWaterfallYAxisIds` (which maps `index` → uid and would pick a copy), before
  `rebindWidgetRefs()`.
- Copies: `uniqueId` from `allocateUniqueId()`, `groupId` from `renumberGroupIds()`,
  `datasetId` = position, `outputWidgets` cleared, `index`/`title`/`units`/`ledHigh`/bands/
  format fields copied. Hidden flagged datasets are skipped (R6).
- Undo: load is outside `ProjectUndoScope`; `applyHistorySnapshot` reuses the core loader but
  snapshots are written without `led`, so the gate never fires on undo.
- Modified: new `DocumentLoadFlags::ledPanelsMigrated`; `setModified(true)` after the load's
  `setModified(false)` and before autosave resumes, plus one `postInfo` (same shape as the
  older-schema notice).
- Layouts: a migrated LED Panel is a new group (new uid); `layout:` entries keyed by group uid
  for the phantom panel were under the *source* group's uid, so the panel's saved geometry is
  not carried over. Workspace refs and external windows persist `(widgetType 8, relativeIndex)`
  and survive.

## Tradeoffs & alternatives considered

Three shapes were sketched before converging:

- **Group Widget, Shared Type** (chosen): new `GroupWidget::LEDPanel`, reuse `DashboardLED = 8`.
- **Group Widget, New Type**: a new `DashboardLEDPanel` pinned at 91 beside Bar Panel. Cleaner
  naming, but every saved layout, workspace ref and external window that stores type 8 would
  resolve to nothing, and `isGroupWidget`, icons and titles would need duplicating.
- **Flag Stays, Builder Cleaned**: keep `led` and only tidy the phantom builder. Rejected by the
  spec's premise check.

| Decision | Options | Chosen + why |
|----------|---------|--------------|
| Dashboard type for the group | reuse `DashboardLED = 8`; new pinned type 91 | Reuse. Type 8 is persisted in layouts, refs and external windows; the model and QML already key on it. |
| Migration gate | raw `led` presence; schema bump to 4 | Presence. The older-schema block clears every workspace list, so a bump would wipe workspaces on every current project unless that block were also narrowed; presence is idempotent by construction. |
| Where generators get their LED Panel | each driver builds its own group; one Core helper | One helper in `core/Core/DataModel/LedPanelGroup.*`, callable from Pipeline and Devices alike, so migrated and generated projects share one shape and one test. |
| Hidden members | hide the LED; show it like Bar Panel | Show, matching Bar Panel (spec R2 amended). The migration skips hidden flagged datasets so today's dashboards are reproduced. |
| Mirror wire version | bump to 2 and regenerate; keep 1 and regenerate fixtures | Keep 1. The protocol (positional snapshots, `(sourceId, uniqueId)` list, hash seed) is unchanged; only the embedded project JSON differs, and the viewer already ignores unknown keys (forward-compat fixture). Fixtures regenerate because they embed the project. |
| `Keys::LED` constant | delete; keep for the peek | Keep with a note. The migration needs the literal, and `registry-verify` only checks manifest keys resolve, not the reverse. |
| Raw-JSON matching | by position; by (title, index) | Position, verified by `title` and `index`, falling back to the pair when a count differs (the reader skips empty objects). |
| Icons | draw `add-ledpanel`; reuse `editor/add-led` and `widgets/led` | Reuse. No new SVGs. |

## Risks & mitigations

- **Workspace wipe via the older-schema block.** Avoided by not bumping `kSchemaVersion`;
  `test_led_panel_migration.py` asserts workspaces survive a reload of the migrated save.
- **Relative-index drift.** Workspace refs and external windows address LED Panels by relative
  index. Inserting each panel directly after its source preserves the phantom order; the
  integration test asserts the order. Data Grid indices are unaffected since no Data Grid is
  added or removed.
- **Duplicate `index` across groups.** Legal today (bit fields), but `migrateLegacyXAxisIds` and
  `migrateLegacyWaterfallYAxisIds` build `index → uid` maps where the last wins; the migration
  runs after both so copies never enter those maps.
- **Generated-file drift.** Every registry artifact regenerates in one step; `sanitize-commit`
  runs `--check`. The API snapshot needs a build: `--check-snapshot` warns locally and fails in
  CI until the maintainer refreshes `api-schema.json` (listed as a maintainer step).
- **gRPC renumbering.** The generator moves 21 to `reserved`; `proto-field-renumbered` in
  `code-verify` guards it.
- **Second copy of the band rule.** `ProjectCheckers::checkLedThreshold` and the editor's band
  prefill both move to "group resolves to `DashboardLED`" through `getDashboardWidget`, never a
  string compare; `tst_alarm_band_applicability` carries the rows.
- **Firmware goldens never compiled locally** (TODO already notes this); the vocabulary change
  is regenerated, not hand-typed, and `check_golden.py` runs in the firmware CI job.
- **Declared controls** set `hideOnDashboard`; one placed in a `ledpanel` group would show as an
  LED, exactly as it would in a Bar Panel. Accepted, documented in Widget-Reference.
- **`common-mistakes.md` classes exposed:** none on the hotpath; the `operator[]`-insert class
  applies to the bucket maps already in `WidgetMapBuilder` and is not touched.
