# Plan 0045 — API Terminal window

> **Phase 2 of 4 — the HOW.** The technical design that satisfies every requirement in
> [`spec.md`](./spec.md). Read the relevant `doc/claude/` sub-docs and the *actual code*
> before writing this — a plan grounded in a stale mental model is worse than no plan.
> Gate: do not start `/ss-tasks` until a human marks this `approved`.

## Approach (one paragraph)

A thin QML-instantiable bridge (`API::TerminalBridge`, no singleton) exposes two things to a
new `Widgets.SmartWindow`-based QML window: `run(input)` — parses `"scope.verb {json}"`,
dispatches through `API::CommandHandler::processCommand()` with `CommandOrigin::Trusted`
exactly like the script `apiCall` gateway, and returns the wrapped response — and
`catalog()` — a one-shot dump of the live `API::CommandRegistry` (name, description,
`inputSchema` properties + required). All UI is QML: a scrollback + input line with a
completion popup on the right/bottom, and a `SearchField`-filtered `ListView` with scope
section headers plus a docs panel on the left. The window is opened by a new registry
command `app.apiTerminal` (icon `commands/api-terminal`, already in rcc) via the
established `DialogLoader` + `app.showApiTerminal()` pattern from `main.qml`. Live registry
over the bundled `api-schema.json` because the registry *is* what generates that file, and
it reflects the build variant (GPL vs commercial command set) for free.

## Architecture & data flow

- **Execute:** QML input `accepted()` → `bridge.run(text)` (GUI thread, synchronous) →
  split first whitespace token as command name; remainder (optional) parsed as a JSON
  object (`QJsonDocument`); parse failure returns `{ok:false, error}` without dispatch →
  `CommandRequest{QUuid id, command, params}` → `CommandHandler::processCommand(request,
  CommandOrigin::Trusted)` → wrapped `QVariantMap` back to QML → appended to scrollback
  (echo line + pretty-printed JSON response). Same dispatch spine as
  `ScriptApiCall.cpp:dispatchApiCall()`; no socket, no server dependency (R2, R10).
- **Discover:** window `Component.onCompleted` calls `bridge.catalog()` once → QML builds
  a JS array `{name, scope, verb, description, params:[{name, type, description,
  required}]}` → drives (a) the ListView model with `section.property: "scope"`, filtered
  by `SearchField` text against name + description (R4), (b) the completion popup
  (prefix/substring match on names) (R3), (c) the docs panel for the selected/typed
  command (R3, R4). Catalog derives from `CommandDefinition::inputSchema`
  (`SchemaBuilder`-built: `properties` map + `required` array) — single source of truth
  (R5).
- **No signals from the bridge**: request/response is pull-only; the bridge holds no state
  beyond nothing (stateless calls into the two existing singletons, same pattern the
  script bridge uses).

## Hotpath & threading impact

- **Touches the hotpath?** No. All work is GUI-thread, user-initiated, outside
  `FrameReader`/`FrameBuilder`/`Dashboard` draw. An open terminal adds zero per-frame
  work. Commands the user runs hit the same handler surface any API client already can.
- **New cross-thread signal/slot?** No. Everything synchronous on the GUI thread.
- **New input to a cached hotpath flag?** No.
- **Timestamp ownership** — untouched.
- `--benchmark-hotpath`: CI gate must stay green (AC10); nothing here runs on the bench
  path.

## Data model & persistence

- None. No `Keys::`, no project JSON, no DB. Window geometry persists via `SmartWindow`
  `category: "ApiTerminal"` (its built-in `Settings` handling, R8/AC7). History is a plain
  QML `var` array, session-only (R6; cross-restart persistence stays an open extension per
  spec).

## API / SDK surface

- None changed. No new command, no handler edit, no generated-surface delta (R10,
  Non-Goals). `app.apiTerminal` is a UI-registry command (spec-0028 surface), not an API
  command.

## QML / UI

- `ApiTerminal.qml`: `Widgets.SmartDialog` (`fixedSize: false`, `contentPadding: 0`,
  preferred 880x560, own `Settings` block for geometry; amended from the planned
  SmartWindow after a live run showed the frameless window's traffic lights overlapping
  the search field — SmartDialog brings the titlebar inset, drag handler, and Close
  shortcut). A 1 px separator under the titlebar tops the content. Two-pane layout:
  - Left: `Widgets.SearchField` above a `ListView` (`section.property` = scope, sticky
    labels); rows show verb + one-line description elided; current item drives the docs
    panel below the list (name, description, parameter table with required markers, from
    catalog); double-click / Return inserts the command name into the input (R4).
  - Right: scrollback (read-only `TextArea` in a `ScrollView`, `monoFont`,
    `TextArea.selectByMouse`, context menu copy/clear/select-all — R7) above a `LineField`
    input row. Completion `Popup` anchored to the input lists matching command names while
    the first token has no trailing space; Tab/Return accepts, Up/Down navigates
    suggestions, Esc closes. With the popup closed, Up/Down walk the history (R6). After a
    known command name is typed, the docs panel follows it (parameter hints, R3).
  - Theme via `Cpp_ThemeManager.colors`, fonts via `Cpp_Misc_CommonFonts`; all strings
    `qsTr()`; no `%n`+`.arg()` mixing.
- No ComboBox restore races (no ComboBox), no editable model-bound fields (input is free
  text — the echo-back landmine doesn't apply).

## Tradeoffs & alternatives considered

| Decision | Options | Chosen + why |
|----------|---------|--------------|
| Catalog source | live `CommandRegistry` vs bundled `api-schema.json` via XHR | Registry — it generates the file; build-variant-correct; no qrc parse. Spec R5 amended to name the registry (same single source). |
| Bridge shape | instantiable QObject vs new singleton + `Cpp_` context property | Instantiable `qmlRegisterType` — no composition-root/census surface, dies with the window; matches per-window bridges elsewhere. |
| Tree widget | ListView + scope sections vs `TreeView` + QModelIndex model vs C++ proxy models | ListView sections — filtering is a trivial JS predicate; a real TreeView needs a C++ tree model for zero user-visible gain at 359 rows. |
| Input syntax | `scope.verb {json}` single line vs separate params editor vs raw NDJSON | Single line — terminal feel, maps 1:1 to the wire mental model; params JSON parse errors reported inline. Parsing lives in C++ (`run(input)`) so QML stays dumb. |
| Completion scope | command names only vs also parameter keys/values | Names only + docs-panel hints (spec R3 floor); value completion is the spec's open question, not built. |
| Destructive verbs | confirmation prompt vs parity with socket | Parity, no prompt (spec open-question lean; terminal is a power tool). |

## Risks & mitigations

- **Dispatch drift** (a second path diverging from the server): mitigated by calling
  `CommandHandler::processCommand()` directly — the identical spine `apiCall` uses; no
  reimplementation of validation or error shaping (R10/AC3).
- **Commercial-guard scan** (`registry-verify` on `Commands/*.qml`): the new binding
  references only `app.showApiTerminal()` — no `Cpp_Licensing_/Cpp_Sessions_/Cpp_MQTT_`
  symbols, so no guard needed; scan stays clean (AC9).
- **Binding coverage**: `contexts: ["app","dashboard"]` + binding in `AppCommandBindings`
  is reachable from both palette models (`[app,dashboard]` / `[dashboard,app]` fallback) —
  the registry-verify binding-coverage check confirms (AC9).
- **Commands with no/empty `inputSchema`**: catalog emits an empty params list; docs panel
  renders "no parameters" — no undefined access.
- **Re-entrancy / teardown hazards**: commands run from a user event on the GUI thread —
  the same context every palette command already runs in; not the mid-parse `apiCall`
  hazard class (that risk is specific to destructive verbs inside frame parsing).
- **Blocking commands** (e.g. long exports) freeze the UI for their duration — accepted:
  identical behavior to the script gateway today; out of scope to make handlers async.
- **i18n**: manifest strings flow through `generate-command-strings.py` (sanitize
  regenerates `CommandStrings.cpp`); QML uses `qsTr` — the `%n`/`.arg()` landmine avoided.
