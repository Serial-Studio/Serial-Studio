# Plan 0105 — Alarms only while visible

> **Phase 2 of 4 — the HOW.** The technical design that satisfies every requirement in
> [`spec.md`](./spec.md). Read the relevant `doc/claude/` sub-docs and the *actual code*
> before writing this — a plan grounded in a stale mental model is worse than no plan.
> Approved 2026-10-28; `/ss-tasks` may start when the maintainer asks for it.

## Approach (one paragraph)

One new GUI-thread object, `UI::WidgetVisibility`, owned by `UI::AlarmMonitor`, computes the
set of dataset `uniqueId`s that are on screen from facts the dashboard already keeps: every
`UI::Taskbar` (one per dashboard view, main and external, enumerated through
`UI::UISessionRegistry`) knows its active workspace and the normal / minimized / closed state
of the windows on it; each view's QML tells its taskbar whether the view itself is shown (a new
`viewShown` property: the main window's Dashboard pane on screen and the window not minimized,
an external window not minimized); the main canvas tells its taskbar which pop-outs are open.
Window ids resolve to datasets through `Dashboard::widgetMap()` and `widgetSlot()`, group-scope
widgets fanning out to their member datasets. The monitor keeps one tracker per alarming
dataset as today, adds the dataset's new `alarmsWhileVisible` flag and a `shown` bit to it, and
answers `tracks(id)` false while a marked tracker is hidden, so the annunciator's existing reap
removes the point; a reveal re-arms the tracker and evaluates it at once from the dataset's
current value as a fresh band entry under the existing cooldown. The flag itself is one more
registry-declared dataset property shaped exactly like `suppressAlarms`.

## Architecture & data flow

Inputs. Each dashboard view owns a `UI::Taskbar` (`Dashboard.qml:64` main, `:341` per external
window) registered in `UISessionRegistry`. A taskbar populates `m_windowIDs` and the
`WindowStateRole` of `m_taskbarButtons` for its active workspace only (`Taskbar.cpp:445-478`),
which is exactly the set the rule needs: windows of hidden workspaces are hidden by definition.
What C++ cannot see today is whether the view itself is on screen and which pop-outs exist;
both are QML facts (`MainWindow.qml:186` `dashboardVisible`, `_extWindow.visibility`,
`DashboardCanvas.qml:76-100` `externalWidgetWindows`) and are pushed down through the two new
taskbar entry points. Those bindings are the only QML logic; the rule lives in C++.

Recompute. `WidgetVisibility` coalesces every input change into one `recompute()` on the next
event-loop turn, so a workspace switch (which fires `activeGroupIdChanged`, `windowStatesChanged`
and `taskbarButtonsChanged` in a row) costs one walk. The walk is bounded by the number of
windows on the shown workspaces plus the pop-outs, and each id resolves through
`Dashboard::widgetMap()` (`Dashboard.h:300`) and `widgetSlot()` (`:295`) the way
`TaskbarWindowMap::findWindowIdByIdentity` already does. Dashboard tools are in the widget map
but never in a taskbar, so they never enter the set. A taskbar that is offline
(`activeGroupId == -1`) contributes nothing.

Gate. `AlarmMonitor::rebuildTrackers` keeps creating one tracker per dataset that passes
`datasetRaisesBandAlarms`, now also recording `whileVisible` and the current `shown`. The runtime
answer to "does this dataset alarm now" has one home, `tracks(id)`, which the annunciator's reap
(`AlarmAnnunciator.cpp:878-898`) already consults on `trackersRebuilt`; `evaluateAlarms` applies
the same answer by skipping a marked, hidden tracker. `applyVisibility()` emits `trackersRebuilt`
after flipping the bits, so the reap runs through the existing path, including its `m_dropHold`
early return (spec 0088 R3), and `refreshConfiguredAlarms()` runs with it at no visible cost.

Reveal. A revealed tracker is uninitialized with `revealPending` set. `applyVisibility()` calls
`processValue` immediately with the dataset's current numeric value: the first-sample branch
seeds `lastFiredBand`, emits `bandTransition` (the annunciator raises a new point, since the old
one was reaped), and, because `revealPending` is set, continues into the notification block,
where the band's severity and the `lastFireMs` cooldown decide whether a notification posts.
`lastFireMs` survives the hide, so flipping tabs inside 3 s cannot repeat a notification (R4).
A reveal with the value in no band, or in an Info / Ok band, seeds silently as a rebuild does.
A hide resets the tracker's band memory so the next reveal is judged fresh, never as a
transition from the band it was in before.

Project edits. The flag rides `Dataset` into the structure snapshot like `suppressAlarms`: an
editor or API toggle marks the runtime dirty, the pipeline re-syncs, the dashboard rebuilds,
`widgetCountChanged` fires and `rebuildTrackers` reads the new flag (R13). Because the taskbar
repopulates on the same rebuild, `WidgetVisibility` recomputes right behind it and the new
tracker's `shown` bit is current within the same tick.

Promptness (R5). Every path is signal-driven on the GUI thread: tab switch, window state,
pane change, window minimize, pop-out open / close and the API's `ui.window.setActiveGroup` /
`setWindowState` all end in the same coalesced recompute, well inside the one-second bound.

## Hotpath & threading impact

- **Touches the hotpath?** No. Nothing runs per frame. `WidgetVisibility` recomputes on UI
  events (user rate), `rebuildTrackers` on dashboard rebuilds (rebuild rate), and
  `evaluateAlarms` keeps its display-tick cadence with one extra bool test per tracker.
  `Dashboard` is read through existing const accessors and is not edited. The `Dataset` struct
  grows by 8 bytes; it is copied on structure snapshots, not per sample, and the span fast lane
  does not touch it. `--benchmark-hotpath` is run once by the maintainer as a formality.
- **New cross-thread signal/slot?** No. Taskbars, the registry, the dashboard, the monitor and
  the annunciator all live on the GUI thread; the one new connection family is GUI to GUI,
  `Qt::AutoConnection` resolving direct.
- **New input to a cached hotpath flag?** No.
- **Timestamp ownership** — not applicable.

## Data model & persistence

One optional dataset key, `alarmsWhileVisible`, written only when true and read with default
false, through the generated serializer. No schema or writer version bump (a bump would send
older files through the migration that drops customized workspaces). Older versions ignore the
key and keep alarming; one that resaves the file drops it. `Keys::AlarmsWhileVisible` is the
single spelling. The mirror's structure message carries the project document verbatim, so a
mirror viewer sees the flag with no wire change; a viewer has its own taskbars and computes its
own visibility.

## Tradeoffs & alternatives considered

Three shapes were sketched before converging: **Tracker bit** (trackers persist, a shown bit
gates them, chosen), **Rebuild on visibility** (a hidden marked dataset gets no tracker and a
reveal rebuilds), and **Annunciator filter** (the monitor is untouched and the annunciator drops
transitions of hidden datasets).

| Decision | Options | Chosen + why |
|----------|---------|--------------|
| Where the gate lives | (a) tracker bit in the monitor; (b) rebuild trackers on every visibility change; (c) filter at the annunciator | (a). (b) loses the cooldown memory and cannot tell a reveal from a rebuild, so a reveal could only seed silently, against R4. (c) leaves the monitor posting notifications for hidden datasets, the same incoherence spec 0093 rejected. |
| Source of visibility | (a) C++ aggregator over the taskbars, QML pushes only the two facts it alone knows; (b) QML computes the visible dataset set and pushes ids; (c) per-widget `visible` reports from delegates, the console annotation pattern | (a). The taskbar already holds the active workspace and the window states in C++, and a delegate's QQuickItem `visible` is true under a minimized window and ignores the pane, so (c) answers the wrong question; (b) puts the rule in QML where no unit test reaches it. |
| Which widgets count as showing a dataset | (a) any widget on screen that shows it, group widgets fanning out to members; (b) band-drawing widgets only | (a), the spec's literal R2: a DataGrid row or MultiPlot curve on screen is the dataset on screen. Applicability still decides whether the dataset can alarm at all, so a plot-only dataset gains nothing from being shown. Reviewer-visible choice. |
| QML bridge | (a) two taskbar entry points (`viewShown`, `setPopOutOpen`); (b) a new root-owned context-property object | (a). The taskbar is already the per-view object QML holds, so no composition-root change and no new global; the aggregator stays private to the monitor. |
| Reveal evaluation | (a) evaluate at once from the dataset's current value; (b) wait for the next `Dashboard::updated` | (a). AC3 requires the point without a new sample, and a silent device would otherwise hold the alarm back indefinitely. |
| Owner of the aggregator | (a) `AlarmMonitor` constructs it in `setupExternalConnections`; (b) `ModuleManager` singleton | (a). The monitor is its only consumer, and the startup contract pins the singleton table; adding an entry needs the ctor-edge proof for nothing. |
| `sizeof(Dataset)` | (a) accept the 8-byte growth; (b) pack the bools | (a). The registry generates plain bool fields; packing would fight the generator for 8 bytes per dataset copied at structure-snapshot rate. |
| Coalescing | (a) one deferred recompute per burst; (b) recompute inline on each signal | (a). A workspace switch fires three taskbar signals in a row; (b) would reap and re-raise within one burst. |

## Risks & mitigations

- **A second copy of the rule.** `datasetAlarmsNow` is the textual home and `tracks(id)` the
  runtime home; `evaluateAlarms` and `applyVisibility` read the same tracker bits. The
  dashboard.md section and the CLAUDE.md row name both, and AC1 pins the table.
- **Reap and drop hold.** `applyVisibility` goes through `trackersRebuilt`, so the annunciator's
  `m_dropHold` return still protects a held table during a link drop (spec 0088 R3). A hide
  during a drop therefore leaves the point until the hold releases, which then reaps it.
- **Stale shown bit at tracker creation.** `rebuildTrackers` reads `isShown()` before the
  taskbar has repopulated for the new structure; the taskbar signals trigger a recompute in the
  same tick and `applyVisibility` corrects the bit. Checked at task time with the AC3 flow; a
  wrong initial bit shows as a point raised then reaped, never as a lost alarm.
- **Taskbars in tests.** The integration suite runs the real GUI, so `viewShown` is bound. A
  taskbar nobody binds defaults to true, so a future view that forgets the binding behaves as
  today, never silently silent.
- **Offline taskbar.** An independent taskbar's `activeGroupId` can be -1 while offline
  (`Dashboard.qml:191-195`); it contributes no windows, which is the right answer.
- **Pop-out of a closed window.** A pop-out counts while open regardless of the taskbar state of
  the same window id (spec R2); the set is a union, so no conflict arises.
- **Qt setter guard and workspace ids.** `setViewShown` and `setPopOutOpen` guard-return on no
  change (common-mistakes "Setter without guard return"); workspace ids stay >= 1000 and are
  never mixed with group ids.
- **TU budgets.** `Taskbar.cpp` 1287 + ~50, `AlarmMonitor.cpp` 283 + ~90, the new TU ~200,
  `Dashboard.cpp` and `AlarmAnnunciator.cpp` untouched. `code-verify.py --tu-census --check`
  before handoff.
- **Generated artifacts shared with other in-flight work.** The generator and
  `sanitize-commit.py` rewrite `proto-fields.json`, the typed proto, the SDK and the search
  index as whole files; checked at task time against the working tree, as spec 0093 did.
- **Snapshot gate.** CI's `--check-snapshot --strict` fails until `api-schema.json` is refreshed
  from a commercial build; the refresh is its own task, sequenced before the commit.
- **Assistant corpus lint.** `dashboard_layout.md` may name the field only after the manifest
  declares it; the skill edit is ordered after regeneration.
- **Translations.** Two new strings; `.ts` files are regenerated by the maintainer's flow, never
  edited here.
