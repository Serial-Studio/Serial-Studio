# Plan 0068 — WebSocket and HTTP/HTTPS clients in the Network driver

> **Phase 2 of 4 — the HOW.** The technical design that satisfies every requirement in
> [`spec.md`](./spec.md). Read the relevant `doc/claude/` sub-docs and the *actual code*
> before writing this — a plan grounded in a stale mental model is worse than no plan.
> Gate: do not start `/ss-tasks` until a human marks this `approved`.

## Approach (one paragraph)

`IO::Drivers::Network` stays one class with one `HAL_Driver` identity and one entry in
`ConnectionManager`; what changes is that its transport selector becomes a first-class
`Network::SocketType` enumerator (`Tcp = 0, Udp = 1, WebSocket = 2, Http = 3`) instead of
`QAbstractSocket::SocketType`, which cannot name either new transport. The WebSocket transport
is a `QWebSocket` member and the HTTP transport is a `QNetworkAccessManager` plus a poll
`QTimer`, both GUI-thread-affine like every other driver, both funnelling into the existing
`publishReceivedData()` so nothing new touches the pipeline. Because both dial asynchronously,
`Network` gains an `isConnecting()` override that is true **only** while a WS handshake or the
HTTP opening request is in flight, and both report through the spec-0050 `reportOpenFinished()`
latch exactly once per attempt — TCP keeps its synchronous `dialTcpBlocking()` verdict path
untouched. The implementation is split **all four ways** behind the unchanged `Network.h`
facade: `Network.cpp` keeps only the shared lifecycle, the four-way dispatchers and the
property model, while `Network/NetworkTcp.cpp`, `NetworkUdp.cpp`, `NetworkWebSocket.cpp` and
`NetworkHttp.cpp` each own one transport end to end — open, close, read, write, verdict and
property block.

## Architecture & data flow

**Translation-unit layout.** One class, one facade header, five TUs — the shape
`ProjectModel` / `ProjectEditor` already use (`app/src/DataModel/Project/`, residual left at the
original path). `scripts/tu-cutter.py` performs the mechanical part: its manifest names
`dest_dir: app/src/IO/Drivers/Network`, `residual: app/src/IO/Drivers/Network.cpp`, and assigns
each existing whole block to its transport TU. The splitter refuses to cut unless the parsed
blocks reconstruct the original file exactly, which is what makes moving the TCP probe stack and
the UDP buffer code safe to do by tool rather than by hand.

The per-transport TUs are reached through one private helper family on `Network`, so the
dispatchers in the residual carry no transport logic of their own:

| Dispatcher (residual) | Delegates to |
|-----------------------|--------------|
| `open(mode)` | `openTcp` / `openUdp` / `openWebSocket` / `openHttp` |
| `close()` | `closeTcp` / `closeUdp` / `closeWebSocket` / `closeHttp` — **all four unconditionally**, see below |
| `write(data)` | `writeTcp` / `writeUdp` / `writeWebSocket` / `writeHttp` |
| `isOpen` / `isReadable` / `isWritable` / `configurationOk` / `isConnecting` | the matching per-transport predicate |
| `driverProperties()` | `appendTcpProperties(list)` etc. — each TU contributes its own rows after the shared Socket Type row |
| `setDriverProperty(k,v)` | `applyTcpProperty(k,v)` etc. — each returns `true` when it consumed the key |

`close()` is the one dispatcher that deliberately does **not** branch on the current socket
type: it tears every transport down. This preserves today's behaviour (the current `close()`
aborts both sockets regardless of mode) and it is what makes a socket-type change while a link
is up safe — branching here would strand a live socket the moment the enum moved. The teardown
finality constraint in the spec depends on this.

Two incidental wins from cutting TCP out: the `#ifdef _WIN32` Winsock-before-Qt include block
stops sitting at the top of a file three other transports must also compile through, and
`onReadyRead()`'s TCP/UDP `if`-chain disappears — each transport wires its own receive slot at
open time instead. That is a signal-wiring change to existing code, and the existing wiring in
`open()` / `dialTcpBlocking()` / `close()` was read in full before planning it.

**Object graph.** `Network` gains three members: `QWebSocket* m_webSocket`,
`QNetworkAccessManager* m_httpManager`, `QTimer m_pollTimer`, plus a `QPointer<QNetworkReply>`
for the one in-flight request. All are created in the ctor and live on the driver's thread —
the GUI thread, exactly like `m_tcpSocket`/`m_udpSocket`. The `QWebSocket` follows the existing
socket lifetime rule (`deleteLater()` in the dtor, never destroyed with the driver) because it
owns a run-loop-registered socket underneath.

**Inbound.** `QWebSocket::textMessageReceived(QString)` and `binaryMessageReceived(QByteArray)`
each capture `CapturedData::SteadyClock::now()` at the top of the slot and call
`publishReceivedData(bytes, timestamp)` — one call per message, satisfying R3. Text messages
are UTF-8 encoded once. On the HTTP side, `QNetworkReply::finished` reads
`reply->readAll()` and publishes it the same way, with the timestamp captured in the slot.
From there both are indistinguishable from a UDP datagram: `HAL_Driver::dataReceived` →
`DeviceManager` → `FrameReader::processData` on the pipeline thread (`DeviceManager.cpp:217`),
an auto/queued hop that already exists.

**Outbound.** `Network::write()` gains two branches. WebSocket: one
`sendTextMessage`/`sendBinaryMessage` per call plus `flush()`, returning the byte count so
`ConnectionManager::writeDataToDevice` echoes it to the console. HTTP: build the configured
request with the written bytes as its body, send it, return the byte count immediately; its
reply publishes through the same `finished` handler as a poll (R8).

**Dial and verdict.** `open()` dispatches on the new enum. TCP and UDP are untouched.
WebSocket: `m_webSocket->open(url)` then return `true`; `isConnecting()` returns true while
`m_wsDialPending` is set; `QWebSocket::connected` → `reportOpenFinished(true)`,
`QWebSocket::errorOccurred` / `sslErrors` (when not ignored) → `reportOpenFinished(false, ...)`
**and** a queued `ConnectionManager::disconnectDevice(this)`, per the io.md rule that every
async dial failure must reach the manager or the connect button wedges. HTTP: fire the first
real request (see tradeoffs) and return `true`; its `finished` handler is the verdict — a 2xx
reports success and publishes the body, anything else reports failure and disconnects. Once
connected, the same `finished` handler switches to the R9 tolerant policy.

**Polling.** `m_pollTimer` (GUI thread, single-shot=false) starts on a successful HTTP open
when the interval is non-zero. Its timeout issues one request only if no reply is in flight;
otherwise it increments a skip counter and returns (R7's zero-interval mode simply never starts
the timer). `close()` stops the timer, aborts and disconnects the in-flight reply, and closes
the WebSocket — after which nothing can deliver or redial, per the spec's teardown constraint.

**Counters.** `m_pollsOk`, `m_pollsFailed`, `m_consecutiveFailures`, `m_pollsSkipped` are plain
`quint64` members incremented in the reply handler and read by `io.network.getStatus` — pulled,
never pushed, matching specs 0033/0035 and `io.opcua.getStatus`. The first failure of a run and
the first success after a failure run each log one console line; nothing logs per poll.

## Hotpath & threading impact

- **Touches the hotpath?** **No.** `FrameReader`, `CircularBuffer`, `FrameBuilder`, the span
  fast lane and the `Dashboard` draw path are not edited. Both transports terminate at
  `HAL_Driver::publishReceivedData()`, which is the existing driver→pipeline seam; the bytes
  that leave it are ordinary `CapturedData`, indistinguishable from UART or UDP bytes. No new
  work is added to any path a TCP or UDP source executes: every new branch is behind a
  `socketType()` test that TCP/UDP already fail. `--benchmark-hotpath` is expected unchanged
  and is run as a regression check, not because the change is near the gate.
- **New cross-thread signal/slot?** **No new one.** WS and HTTP publish through the
  `dataReceived` connection that `DeviceManager` already owns (GUI → pipeline, auto/queued).
  Per-message publishing matches what UDP has always done per datagram; nothing here introduces
  a `BlockingQueuedConnection`, and nothing crosses into the pipeline thread from a new object.
  The one queued call added is `ConnectionManager::disconnectDevice(this)` on an async dial
  failure — queued because the failure arrives from inside the socket's own error emission, the
  same reason `onErrorOccurred()` already queues it.
- **New input to a cached hotpath flag?** **No.** `m_operationMode`, `m_anyAsyncSink`,
  `m_captureLatestFrame`, `m_changeDriven` and `Dashboard::m_streamAvailable` take no input from
  the driver's transport choice. `isStreamCapable()` stays `false` — neither transport is a
  dense typed sample source, so the spec-0051 stream lane is not involved.
- **Timestamp ownership.** Source owns time: `SteadyClock::now()` is captured at the top of
  each receive slot — the WebSocket message handlers and the HTTP `finished` handler — and
  passed to `publishReceivedData(data, timestamp)`. Nothing re-stamps downstream. This is the
  exact `common-mistakes.md` "Timestamps" entry: the timestamp is taken in the callback, not
  defaulted at a later forwarding hop.

## Data model & persistence

No `Frame.h` `Keys::` additions, no schema version bump, no Sessions DB change.

Persistence rides the existing generic mechanism: `ProjectModel::captureSourceSettings()`
(`ProjectModelSources.cpp:293`) serializes whatever `driverProperties()` returns, and
`HAL_Driver::applyConnectionSettings()` replays it through `setDriverProperty()`. Adding the new
properties to those two functions therefore satisfies R13 for project files with no serializer
change. `QSettings` persistence follows the existing `NetworkDriver/*` group with new keys
(`wsUrl`, `httpUrl`, `httpMethod`, `httpBody`, `httpHeaders`, `httpInterval`, `ignoreTlsErrors`,
`wsMessageFormat`).

**Migration:** none needed and none written. `socketTypeIndex` 0 and 1 keep their values, so an
existing project's stored settings deserialize unchanged; a project written by a newer build and
opened by an older one falls into `setSocketTypeIndex()`'s `default: break`, which leaves the
old build on its previous socket type rather than crashing. The new keys are absent from old
projects and fall back to their defaults.

`ProjectEditorCommit.cpp:139`'s `kModeKeys` already contains `socketTypeIndex`, so switching to
WebSocket or HTTP in the Project Editor rebuilds the source form and reveals the new fields with
no change there.

## Tradeoffs & alternatives considered

Three candidate shapes were sketched before settling: **Fat driver** (everything inside
`Network.cpp`), **Transport strategy** (an abstract transport interface with four
implementations), and **Same class, per-transport TUs** (one `Network` class, one TU per
transport behind the facade header).

| Decision | Options | Chosen + why |
|----------|---------|--------------|
| Driver structure | (A) Fat driver — all four transports in `Network.cpp`, ~1700 lines; (B) Transport strategy — abstract interface + 4 impls, cleanest separation but a class hierarchy the `ConnectionManager`/`CLI`/`NetworkChecks` consumers would have to reason about; (C) Same class, per-transport TUs | **C, split all four ways** (maintainer call, 2026-08-25). It is the repo's existing answer to this problem (`ProjectModel`/`ProjectEditor` behind one facade header) and it keeps the single `Network*` every consumer holds. Splitting only the *new* transports was considered and rejected: it buys a smaller diff at the cost of a residual where TCP and UDP stay tangled while WS and HTTP are clean — separating halfway is the worse end state. |
| Cut mechanism | (A) `scripts/tu-cutter.py` manifest for whole blocks + hand extraction for the branch bodies; (B) All by hand | **A.** The splitter's refuse-unless-it-reconstructs-exactly check covers the bulk move (probe stack, dial, UDP buffer). Only the bodies extracted *out of* the `open`/`close`/`write`/`onReadyRead` branches are hand work, and they are reviewed as a behaviour-preserving refactor in their own task. |
| Transport enumerator | (A) Keep `QAbstractSocket::SocketType`, invent sentinel values; (B) Nested `Network::SocketType` Q_ENUM; (C) `SerialStudio::NetworkSocketType` in the global vocabulary header | **B.** Qt's enum cannot legally name a WebSocket or an HTTP client, so (A) is a lie in the type system. Only the driver, `NetworkChecks.cpp:242` and the tests use the typed form — everything else crosses the boundary as the integer index — so the global header (C) would buy nothing. |
| HTTP Connect verdict | (A) A separate `HEAD`/`GET` probe before the first poll; (B) The first real configured request *is* the probe, and its body is published; (C) No probe — connect optimistically | **B.** (A) issues a `HEAD` that many REST endpoints answer with 405, turning a healthy API into a failed connect, and for a `POST` mode it means two side-effecting requests per session. (B) gives R11 its verdict with no extra traffic and delivers an initial reading immediately. (C) fails R11. |
| Headers editor | (A) One `Text` driver property, `Name: Value` per line; (B) A new `DriverProperty::KeyValueList` type | **A.** (B) would touch the generic property form renderer used by every driver's Project Editor page — scope well outside this spec. A single string persists through `captureSourceSettings()` with no serializer change and renders as a `TextArea` in the Setup pane. |
| WebSocket text vs binary on write | (A) Always binary; (B) Always text; (C) Auto — text when the payload is valid UTF-8, binary otherwise, with an explicit override property | **C.** `HAL_Driver::write()` receives bytes with no mode information (the console's `DataMode` never reaches it), and the choice is visible to the peer: a JS client's `onmessage` gets a `string` or a `Blob` depending on it. Auto is right almost always; the override property exists for the case where it is not. |
| Poll overlap | (A) Skip the tick, count it; (B) Queue requests; (C) Shorten the next interval | **A** (spec-resolved). Queueing an unbounded request backlog behind a slow endpoint is the failure mode `OpcUaSession`'s "ONE read outstanding" rule exists to prevent. |
| Failure counter surface | (A) API-only (`io.network.getStatus`) + console lines on transition; (B) A new GUI status pane | **A.** The spec asks for the counts to be *visible as driver diagnostics*, not for a new UI surface; a status pane is a separate feature. **Flagged for review** — say so if a GUI readout was intended. |
| `isConnecting()` override | (A) Override, true only during a WS handshake / HTTP opening request; (B) No override, make both dials block like TCP | **A.** (B) would mean spinning a nested event loop inside `open()` for a `QWebSocket` handshake, which is precisely the "never abort-and-redial a run-loop-registered socket" and nested-loop hazard io.md documents. The override returns `false` for TCP and UDP, so the existing sync doctrine is untouched. |

## Risks & mitigations

- **Regressing TCP or UDP while splitting them out.** This is now the largest risk in the plan
  and it is a self-inflicted one: the spec changes nothing about TCP/UDP behaviour, yet the
  four-way split moves and re-shapes their code. The hazards are specific — the Winsock-first
  include order must survive the move into `NetworkTcp.cpp`; `dialTcpBlocking()`'s
  wire-handlers-only-on-success rule and the throwaway-probe-per-attempt rule are load-bearing
  against the 2026-08-10 macOS `readFromSocket` crash; the UDP multicast join must stay ordered
  after `bind()` and before the `QIODevice::open()`; and `close()` must keep tearing down every
  transport rather than only the selected one. *Mitigation:* the split lands as its own
  task with **no behaviour change and no new transport in the same step**, driven by
  `tu-cutter.py` (which refuses a cut that does not reconstruct the file exactly) for the whole
  blocks; the hand-extracted branch bodies are diffed function-by-function against the
  originals; and TCP + UDP are re-verified against `DeviceSimulator` before the WS/HTTP work
  starts. The split step is separately revertable.
- **A wedged Connect button** — the bug class spec 0050 exists to kill. Both new modes dial
  async, so a path that reports only success (or reports twice) breaks the toolbar. *Mitigation:*
  every terminating WS/HTTP outcome funnels through one private `failDial(reason)` /
  `succeedDial()` pair; `reportOpenFinished()`'s base-class latch makes a double report a no-op;
  `close()` disarms. AC3's "connect to a closed port, then reconnect" observation is the check.
- **A late callback into a torn-down driver.** `QWebSocket` and `QNetworkReply` both deliver
  asynchronously, and a reply outliving `close()` would publish into a dead session.
  *Mitigation:* `close()` aborts and `disconnect()`s the in-flight reply and stops the timer
  before returning; the reply pointer is a `QPointer`; the `QWebSocket` is `deleteLater()`'d in
  the dtor rather than destroyed inline, following the 2026-08-16 macOS rule already recorded in
  `Network::~Network()`.
- **Silent double-delivery on a redirect.** A followed redirect that also fires `finished` on the
  original reply would publish twice. *Mitigation:* publish only from the final reply object and
  only once per request (guarded by clearing the in-flight pointer first).
- **TLS bypass leaking into a shipped project.** `ignoreTlsErrors` persists into the project file
  like any other property. *Mitigation:* default off, and the console states the bypass on every
  connect that uses it (R10), so it cannot be silently inherited.
- **`configurationOk()` / `open()` disagreement** — the failure mode this driver already fixed
  once for DNS. *Mitigation:* both call one shared `urlForCurrentMode(QUrl&, QString& reason)`
  helper; there is no second validation rule.
- **Stale generated API artifacts.** New commands do not reach `api-schema.json` without a build.
  *Mitigation:* the tasks list makes the `--dump-api-schema` refresh an explicit maintainer step
  before `sanitize-commit.py`; `code-verify.py`'s staleness check fails CI otherwise.
- **`%n` / `.arg()` in new translated strings** — the recurring new-feature breakage in
  `common-mistakes.md`. *Mitigation:* numbered placeholders only in every new `tr()`/`qsTr()`.
- **Qt6::WebSockets availability.** `scripts/install-qt.sh` installs the `qtN-full` alias, so CI
  already has the module; it is LGPLv3, so the GPL build is unaffected. *Residual risk:* any
  packaging manifest that enumerates Qt libraries explicitly needs the new one — checked during
  implementation.
