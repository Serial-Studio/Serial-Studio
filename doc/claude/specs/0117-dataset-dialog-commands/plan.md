# Plan 0117 — Palette and context-menu commands for the dataset dialogs

> **Phase 2 of 4 — the HOW.** The technical design that satisfies every requirement in
> [`spec.md`](./spec.md). Read the relevant `doc/claude/` sub-docs and the *actual code*
> before writing this — a plan grounded in a stale mental model is worse than no plan.
> Gate: do not start `/ss-tasks` until a human marks this `approved`.

## Approach (one paragraph)

Three catalog commands, `editor.editAlarmBands`, `editor.editValueLabels` and
`editor.editFrequencyMarkers`, each bound twice. The editor palette's binding set runs the
existing selection openers. The context-menu binding set runs new per-target openers with the
right-clicked row's ids, the shape Edit Transform Code already uses
(`openTransformEditorFor(groupId, datasetId)`). Each dialog's applicability becomes one C++
predicate over a dataset. The toolbar, the palette and the menu all ask that predicate, so
the Frequency Markers rule leaves the toolbar's QML expression and the Alarm Bands rule stays
the spec 0093 one. The dialogs, their hosts and their commit paths are unchanged: each commit
already resolves the dataset by the uniqueId captured when the dialog opened, and already
leaves the selection alone when that dataset is not the selected one.

## Architecture & data flow

Menu path: right-click → host `setTarget({kind: KindDataset, id: datasetId, parentId: groupId})`
→ `CommandMenu` creates entries whose binding is visible →
`Cpp_JSON_ProjectEditor.openXEditorFor(groupId, datasetId)` → `EditorForms` resolves the
dataset (the selected dataset's in-editor copy when the ids match it, otherwise the model's)
→ the existing `openXEditor(...)` signal with that dataset's payload, and for Alarm Bands and
Frequency Markers the captured `m_*DialogUniqueId` → the dialog host already in
`ProjectEditor.qml` / `DatasetView.qml` shows it → Apply → the existing `commitX(...)`, which
resolves by uniqueId and updates only that dataset, as one undo step.

Palette path: the palette joins `ProjectEditorCommandBindings`; each entry's `visible` reads
notifying properties (`currentView`, `selectedDatasetEnabled`, `alarmBandsApplicable` /
`frequencyMarkersApplicable`), so it is current whenever the palette opens; `run()` calls the
selection opener the toolbar calls.

The lock needs no new gate: while the project is locked the editor layout is disabled under
its overlay (no right-click reaches a row) and every editor shortcut, the palette's included,
is disabled.

### Amendment 1 (2026-11-09, during implementation)

The three dialogs were hosted inside `DatasetView.qml` (all three) and `MultiSelectionView.qml`
(Alarm Bands), which exist only while the editor shows them. A menu opened from the flow
diagram, or inside a multi-selection, would emit the open signal with no host loaded, or with
two. The hosts move unchanged into `ProjectEditor.qml`, as the frame parser test dialog already
is, so each dialog has exactly one host whatever the editor shows. A side effect: an open dialog
no longer closes when the selection changes; its commit already resolves the dataset by the
uniqueId captured at open, so that is safe within one project. That uniqueId is positional, so
the editor window closes the three dialogs when the project path changes (another project, New,
Save As; a plain save re-announces the same path) and when the editor hides, as it already does
for its icon pickers.

## Hotpath & threading impact

- **Touches the hotpath?** No. Project Editor GUI code and command manifests only.
- **New cross-thread signal/slot?** No. Every call is GUI-thread, user-action rate.
- **New input to a cached hotpath flag?** No.
- **Timestamp ownership** — not applicable; no data path is touched.

## Data model & persistence

None. No project key, no QSettings key, no change to how bands, labels or markers are stored.

## API / SDK surface

None. The commands are UI catalog entries; the API already edits the three fields. The
driving surface (spec 0101) addresses the new menu items and palette cards by command id with
no extra work.

## QML / UI

Three menu entries in the dataset menu (tree and flow diagram) and three palette entries.
Hidden, not dimmed, where they do not apply (spec R5); the toolbar keeps its disabled buttons.
No new dialog, no motion, no new icon (Frequency Markers borrows `editor/fft`, as its toolbar
button does, until `editor/frequency-markers` is drawn).

## Tradeoffs & alternatives considered

| Decision | Options | Chosen + why |
|----------|---------|--------------|
| How a menu entry reaches its dataset | A. select the target, then run the selection opener; B. per-target openers; C. compute availability in QML from dataset fields | **B.** A changes what the flow diagram shows (spec R2). C copies the spec 0093 rule into QML, the orphan-alarm class spec R4 forbids. |
| Command ids | one id per dialog bound in both sets; separate `editor.menu.*` and palette ids | **One id per dialog.** One title and tooltip each to translate, and the two binding sets never meet (the palette joins only `ProjectEditorCommandBindings`), as `dashboard.autoLayout` already does across two sets. |
| Where "dataset enabled" is checked | inside the per-target predicate; in each binding | **Inside the predicate for the menu, `selectedDatasetEnabled` for the palette.** The toolbar already gets it from the disabled dataset view, and a disabled dataset's toolbar opens nothing, so its menu entries are hidden too. |
| Frequency Markers toolbar rule | keep the QML expression; read the new property | **Read the property.** Otherwise the toolbar and the menu are two copies of the rule. |

## Risks & mitigations

- **A stale target after a model rebuild.** The menu's ids are positional. Mitigation: the
  resolver bounds-checks them, and the commit resolves by the uniqueId captured at open, so a
  dataset removed while its dialog is open commits nothing (existing behavior).
- **A menu-opened dialog for the selected dataset.** The commit treats the selected dataset's
  in-editor copy as the truth. Mitigation: the resolver hands the dialog that same copy when
  the ids match the selection, so both paths agree.
- **`EditorCommit.cpp` is 9 lines under the TU limit.** Mitigation: only a signature change
  lands there; new code goes to `EditorForms.cpp` (1439) and `ProjectEditor.cpp` (1411).
- **Translations.** New titles must reach `CommandStrings.cpp` before the translation update;
  `generate-command-strings.py --check` gates it.
