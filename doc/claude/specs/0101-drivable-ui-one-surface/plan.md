# Plan 0101 — Drivable UI and One Command Surface

> **Phase 2 of 4 — the HOW.** The technical design that satisfies every requirement in
> [`spec.md`](./spec.md). Read the relevant `doc/claude/` sub-docs and the *actual code*
> before writing this — a plan grounded in a stale mental model is worse than no plan.
> Gate: do not start `/ss-tasks` until a human marks this `approved`.

This plan designs **Part A (the driving surface) in full** and carries Parts E, C and D as
outlines with their files, data flow and risks. The spec lands the four parts as four squashed
commits (R27); each later part gets a plan addendum (`plan-e.md`, `plan-c.md`, `plan-d.md`) in
this folder before its own `/ss-tasks`, so the review that matters for each happens when its
ground truth is current rather than three commits early.

## Approach (one paragraph)

Part A adds one handler in the Ui layer, beside the existing dashboard-window handler, that
registers six `ui.automation.*` commands and reads or drives the live Qt Quick windows through
public Qt API only: windows from `QGuiApplication::topLevelWindows()`, the element catalog from
a bounded walk of each `QQuickWindow`'s item tree (visibility, enabled state, geometry mapped to
window coordinates, role from the control's type, label and text from dynamic properties, the
identifier from `objectName`), input through `QWindowSystemInterface` with synchronous delivery
(the path `QTest` itself uses, which keeps the application's button and modifier state
coherent), and screenshots through `QQuickWindow::grabWindow()` with the inverse HDR transfer
applied when the swapchain is FP16. Identifiers come from a QML sweep: manifest-driven delegates
take their command id, hand-built controls take literal dotted names, repeated delegates fold in
the identity of the item they show, and every top-level window names itself. Gating is a new
`DrivesUi` capability answered by a third session-scoped `ConsentGate`. The walk, the input
synthesis and the capture are four small classes under `core/Ui/UI/Automation/` so a ctest can
exercise them against an offscreen `QQuickView` fixture without the application.

## Architecture & data flow

### Where it runs

Every API command runs on the GUI thread: the server's worker thread owns only sockets and
hands each message to the server object, which executes the registry inline. The six handlers
therefore read the Qt Quick tree without locks and deliver input synchronously; the reply is
built after delivery returns. Nothing in Part A opens an event loop: synchronous delivery
through `QWindowSystemInterface` dispatches the event before returning, and `grabWindow()` on
the threaded render loop blocks on a wait condition for the render thread, not on an event
loop.

### Window inventory

`QGuiApplication::topLevelWindows()` filtered to visible `QQuickWindow`s. A window's id is its
`objectName`; the sweep gives every window root one. Fields: id, title, frame geometry in
screen pixels, `devicePixelRatio`, active (equal to the focus window), modal (any visible popup
under the window's overlay whose popup object reports `modal`), and `focusedId` (the nearest
catalogued ancestor of `activeFocusItem()`). Headless runs load no QML, so the list is empty
and every other command answers an execution error naming that.

### Element catalog

An iterative depth-first walk from `contentItem()` with an explicit stack, a depth cap of 64
and an item cap of 16384 (the CSD container and the HDR wrapper each add a level; the walk
assumes no structure). An item is listed when it is visible with non-zero opacity and its type
classifies as a control:

- Qt Quick Controls types by class name prefix: `QQuickButton`, `QQuickToolButton`,
  `QQuickRoundButton`, `QQuickItemDelegate` → `button`; `QQuickCheckBox` → `checkbox`;
  `QQuickRadioButton` → `radiobutton`; `QQuickSwitch` → `switch`; `QQuickTabButton` →
  `pagetab`; `QQuickMenuItem` → `menuitem`; `QQuickComboBox` → `combobox`;
  `QQuickTextField`, `QQuickTextInput`, `QQuickTextArea`, `QQuickTextEdit` → `editabletext`;
  `QQuickSpinBox` → `spinbox`; `QQuickSlider`, `QQuickRangeSlider`, `QQuickDial` → `slider`.
- The repository's own Item-based controls by QML component name, read from the class name
  up to `_QMLTYPE_`: `ToolbarButton`, `TaskbarButton`, `BigButton`, `MenuButton` → `button`;
  `SegmentedControl` → `pagetab`; `SearchField` → `editabletext`; `WidgetTitleBar` → `tile`.
  Every one of these declares properties, so Qt gives it a dynamic meta-object named after the
  component; the ctest pins that, and the sub-doc lists it beside `_qt_sg_hdr_format` as a
  name to re-verify per Qt bump.

A named item of no classified type is listed with the role `item`, so a hand-built delegate
(a palette card, a start-menu entry) becomes reachable by being named; an unnamed plain item
is never listed. Each entry carries `id` (`objectName`, possibly empty), `role`, `label` (the `text`, `title`,
`placeholderText` or `toolTip` property; manifest-driven controls carry their title as `text`,
and the manifest itself is loaded in QML, so there is no C++ title lookup), `text` for editable
roles (the combo's current entry and a spin box or slider value included), `x`/`y`/`width`/`height` from
`mapRectToScene` in window coordinates, `enabled`, `checked` when the property exists, and
`focused`. Filters: `id` substring, `label` substring. Resolution by id returns the first
match in walk order; resolution by point returns the last listed control whose rect contains
it, which is the topmost.

### Click and key

Click resolves the target (id or coordinates), refuses an invisible or disabled control or a
point outside the window, then delivers move, press and release (double: press, release,
double-click press, release) through
`QWindowSystemInterface::handleMouseEvent<SynchronousDelivery>` with the chosen button and
modifiers. The reply reports the control under the point after delivery and the coordinates
used. Key accepts `keys` (a `QKeySequence` string, the notation the manifests use) or `text`
(one press and release per character, with the character as the event text) delivered through
`handleKeyEvent<SynchronousDelivery>`; a `target` id calls `forceActiveFocus()` first. Qt Quick
routes key events to the active focus item and shortcuts fire from the window, so no item
addressing is needed beyond focus.

### Screenshot

`grabWindow()` returns the rendered window. With HDR output active the swapchain is FP16 scRGB
and the grab comes back in an FP16 format with SDR white above 1.0; `WindowCapture` applies the
inverse of the output transform (divide by the SDR white scale, linear to sRGB with the
constants from `Misc/HdrTransfer.h`) and converts to 8-bit. Otherwise the 8-bit grab is used
as is. Optional element crop (rect times `devicePixelRatio`) and `scale` (0.1 to 1.0), PNG
encoded into a `QBuffer`, base64 in the reply with `width`, `height` and `scale`. The encoder
halves the scale until the PNG is under 4 MiB, so a reply never exceeds the server's message
limits.

### Reduce motion

`setReduceMotion {enabled}` calls the existing persisted setter on the graphics backend and
returns the previous value; the pytest fixture restores it. It is a preference command, not a
driving command, and sits in the safe tier.

### Gating

`CommandCapabilities::of()` reports `DrivesUi` for `click` and `key`. `authorizeRemoteCommand`
routes it to `m_uiDrive.authorize()`: allowed, consent required (the prompt is queued once
through the existing message-box path; the command is refused meanwhile), or denied on the
offscreen platform without the auto-consent variable. The variable grants all three gates in
the constructor, as it does the two today. Nothing else in the remote gate moves. The prompt:
title "Allow API clients to drive the user interface?", body naming what a click can do
(connect, save, delete) and that it acts as the user would.

The assistant resolves the names through `command_safety.json` as the spec's R8 states;
`isDispatcher()` and `plannedCommands()` are untouched because none of the six dispatches.

### Identifier convention

| Control kind | Identifier |
|--------------|------------|
| Manifest-driven (ribbon, menus, palette, start menu) | the command id, e.g. `io.toggleConnection` |
| Hand-built control | lowercase dotted literal `<area>.<control>`, e.g. `console.send`, `setup.uart.baudRate` |
| Repeated delegate | `<area>.<kind>.<identity>.<control>`, e.g. `dashboard.tile.3.close`, `taskbar.window.7` |
| Window | the file's camelCase name: `main`, `settings`, `projectEditor`, `assistant`; `external.<widgetIndex>` |

`widgetIndex` is the tile identity because it is what the window manager keys tiles by and it
is stable for a project within a session; a dataset id would need a lookup and does not exist
for group tiles.

## Hotpath & threading impact

- **Touches the hotpath?** No. No file under the frame pipeline or the dashboard draw path
  changes. The catalog is built per request; nothing is maintained per display tick.
- **New cross-thread signal/slot?** No. The handlers run on the GUI thread, where the Qt Quick
  tree lives. `grabWindow()` synchronises with the render thread through Qt's own wait, which
  already happens for every window grab in Qt.
- **New input to a cached hotpath flag?** No.
- **Timestamp ownership.** Not applicable; no frame data is produced or consumed.
- **GUI-thread cost.** A catalog walk is microseconds per item; a full-window grab is one
  extra render plus a readback (tens of milliseconds at 4K), request-rate only.

## Data model & persistence

None. No project JSON key, no schema bump, no sessions table. The reduce-motion setter persists
to its existing `App/ReduceMotion` key, which is the setter's current behaviour, not a new
store. The consent gate is session-only, like the two it joins.

## QML / UI

No visual change. The sweep adds `objectName` lines and, in `CommandMenu`, one creation
property. The two linter rules make the convention mechanical:

- `qml-objectname-literal`: the expression bound to `objectName` is a string literal, a
  `node.id` / `modelData.id` / `entry.id` form, or a concatenation of literals with identity
  properties; any `qsTr(`, theme reference or `.title` / `.text` / `.label` read inside it is
  an error. Blocking everywhere, including files the sweep has not reached.
- `qml-control-unnamed`: in `app/qml/Widgets/Command*.qml`, `app/qml/MainWindow/**` and
  `app/qml/Dialogs/Settings/**`, an instance of a shared interactive widget or a raw Qt Quick
  control whose body has no `objectName:` line is an error; advisory elsewhere until Part D
  widens the scope.

## Risks & mitigations

- **Qt type names are not API.** `_QMLTYPE_` suffixes, `QQuickPopupItem` under the overlay and
  the control class names are implementation names. The ctest pins every one, and the new
  sub-doc lists them beside `_qt_sg_hdr_format` as a per-Qt-bump check.
- **A click can open a native dialog.** Pressing a control bound to a file-dialog command
  blocks the GUI thread in a platform modal loop and the command never returns until a human
  dismisses it. The spec names native dialogs a non-goal; the API reference says so next to
  `click`; tests use the path-taking commands. No code guard, because the catalog cannot know
  which commands open one.
- **The consent prompt is a modal message box.** It is queued, so the refusing command returns
  first, as device-write consent does today. A maintainer running the security test sees the
  prompt once and answers it; the docstring says so.
- **Payload size.** A 4K grab is megabytes of base64. The 4 MiB cap and the scale halving keep
  it under the server's message limits; Part E downsizes further before anything reaches a
  model.
- **Entrance animations.** Replies wait for visibility, not animation end; a test that compares
  pixels sets reduce motion first through the sixth command.
- **CSD and the HDR wrapper reparent the content tree.** The walk assumes no structure and the
  depth cap is far above the real depth; the pytest covers the real main window.
- **The registry ctests sweep the schema snapshot.** Forgetting `--dump-api-schema` fails
  three ctests by name, which is the intended backstop; the task list makes it a step.
- **Tier fallthrough.** An unlisted name resolves to confirm in the assistant. The static tests
  pin the six names to their tiers.
- **The security test needs a no-consent instance.** It follows the existing
  `SS_TEST_AUTO_CONSENT` convention and skips under auto-consent; the ctest on `ServerAuth`
  covers non-composition without a prompt.
- **Silent-breakage classes from `common-mistakes.md`:** nested event loops (none opened),
  the setter-without-guard rule (the gate and the capture have none), and the
  subagent-report rule (every file and line this plan leans on was spot-checked in the tree).

### Part E: assistant image support

- **Data flow.** A tool result whose JSON carries a `png` field is recognised by
  `ToolTurnRunner`, which stores the blob through `ChatStore` and keeps a reference on the
  card; `Conversation` hands the provider a history whose image-bearing tool results and user
  messages are encoded by `ProviderJson` in each vendor's shape (Anthropic base64 image block,
  OpenAI data-URL `image_url`, Gemini `inlineData`), or replaced by the text note when
  `ProviderCapabilities::supportsImages` is false. `LocalProvider` and the compatible vendors
  read the capability from the endpoint's model report where present and from a per-model
  toggle otherwise. `TokenBudget` charges images at the vendor's per-image estimate and keeps
  the newest three verbatim. The composer accepts paste and drop of PNG and JPEG (four per
  message, 4 MiB each), shows thumbnails, and registers nothing with the file sandbox because
  the bytes travel with the message. Captures are downscaled to a 1280 px long edge before
  encoding. `MetaToolCatalog` adds `ui.automation.screenshot` to the essential roster; the
  skill files tell the model to look before it acts.
- **Risks.** The vendor tool-result byte budgets would truncate base64, so images bypass the
  text budget; `Redactor` must not scan image bytes; chat store growth is bounded by the
  retention rules; the approval card must render the capture before approval (R24).

### Part C: connection setup panels

- **Data flow.** A new `API::UiOriginScope` on the registry: `execute()` under it records the
  undo step and the modified flag as today but skips the pre-mutation snapshot, the autosave
  arming and the backup path in the reply, and opens no `RemoteDispatchScope`, so licensing
  sees a local origin and the assistant's tiers do not apply. `UI::UiDispatch`
  (`Cpp_UI_Dispatch.run(name, params)`) is the one QML entry: it opens the scope, executes, and
  routes a refusal or failure to the existing notice path (R13). The 14 panels replace each
  two-way driver write with a `run()` of the matching `io.<driver>.set*`; readbacks stay
  bindings. Drivers without setters gain them with the full ritual.
- **Risks.** Apply-live versus apply-on-connect timing is unchanged because the dispatch is
  synchronous; the combo restore-race guards stay on the readback side; the structural count
  of direct writes must reach zero before the rule turns blocking.

### Part D: Project Editor

- **Data flow.** The same `UiDispatch` with a coalesce key parameter that forwards to
  `setNextUndoHint` before per-keystroke commands, so a title burst stays one step; the
  registry's own undo frame remains the composite boundary. Dialogs stay in QML and dispatch
  after confirmation; importer and generator flows end in `project.open`. The 131 `project.*`
  commands are inventoried against the 850 mutating call sites first, and the gaps are added
  with the ritual.
- **Risks.** Per-keystroke serialization (R19) if the UI scope fails to skip the registry's
  snapshot; selection and expansion must stay direct; the linter rule's whitelist must name
  the view-state calls the spec keeps direct.
